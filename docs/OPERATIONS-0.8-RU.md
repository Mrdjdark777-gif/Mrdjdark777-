# True Thrills 0.8 — сервер и восстановление

Подготовлено 9 сентября 2026. Эти действия ещё не выполнялись на VPS. Команды рассчитаны на существующую установку `/opt/truethrills`, Node 22, nginx и службу `truethrills`. Не отправляй содержимое `.env`, SSH-ключи, Firebase service account или APK signing key в чат.

## Обновление

Изменения находятся в `codex/stabilize-0.8`; до принятия проверок это тестовая ветка. Основная ветка — `claude/read-link-content-h18psv`. Не использовать `git reset --hard` и не заменять актуальные изменения Claude старым архивом.

Для первого перехода с 0.5 сначала остановить эфир и службу, сохранить базу/аудио прежним скриптом, **отдельно сохранить `.env`**, затем переключить код с чистым рабочим деревом на нужную проверенную ветку. `.env` не включать в публичные архивы исходников.

```bash
cd /opt/truethrills
git status --short
git fetch origin
```

Если есть локальные изменения, сначала сохранить их в отдельной ветке/коммите. Проверить текущий SHA и SHA версии для обновления. Далее в согласованное время без эфира:

```bash
sudo systemctl stop truethrills
sudo install -d -m 700 /var/backups/truethrills
sudo node --env-file=.env scripts/backup-data.mjs /var/backups/truethrills
```

Скрипт 0.5 не копирует `.env`. Скопировать его в созданную папку копии как `server.env` с правами 600. Проверить, что база и аудио присутствуют. Сохранить прежний commit SHA. Не продолжать при ошибке backup.

Для тестовой установки использовать `git switch --track origin/codex/stabilize-0.8` (если локальной ветки ещё нет). Если ветка уже существует — переключить её и выполнить `git merge --ff-only origin/codex/stabilize-0.8`. Для обычного выпуска после принятия изменений аналогично использовать основную ветку.

```bash
npm ci --include=dev
npm run build
node --env-file=.env node_modules/drizzle-kit/bin.cjs migrate
sudo systemctl start truethrills
curl --fail https://truethrills.com/api/health
```

На старом VPS проверить, что nginx задаёт `proxy_set_header X-Real-IP $remote_addr;`, а Next слушает 127.0.0.1:3000. Только после этого выставить `TRUST_PROXY=true` в `.env`. Без этого лимит входа общий для всех адресов. Существующая TLS-конфигурация nginx сохраняется.

При следующих обновлениях уже установленной 0.8 есть `sudo bash scripts/update-safe.sh`: он проверяет чистоту кода и возможность fast-forward, отказывается работать во время эфира, делает копию до изменения кода, затем строит приложение и применяет миграции. При ошибке останавливает службу и выводит прежний SHA для ручного восстановления. Автоматического отката базы нет.

## Резервные копии

```bash
sudo bash scripts/install-operations.sh
sudo systemctl start truethrills-backup.service
sudo systemctl status truethrills-backup.service --no-pager
sudo systemctl list-timers 'truethrills-*'
```

Ежедневная копия — в 04:00 по времени VPS. При активном эфире она откладывается до следующего запуска таймера. Проверка мониторинга выдаст ошибку, если нет подтверждённой копии за 36 часов. Во время копирования служба останавливается, чтобы удаление публикации не рассогласовало базу и файлы. После успеха или сбоя backup прежняя активная служба запускается снова.

Копия содержит SQLite, `storage`, `.env` как `server.env` и `VERIFIED.json`. Проверяются целостность SQLite, наличие аудио и размер из метаданных. В копии есть приватные токены подписок и пароль/секреты сервера: хранить её приватно. Автоматическое удаление старых копий пока не включено; следить за диском и удалять только после подтверждения отдельной копии.

Проверка выбранной папки:

```bash
node scripts/verify-backup.mjs /var/backups/truethrills/TrueThrills-ДАТА
```

Обязательна копия **вне VPS**, например на собственном Windows ПК. Копирование на тот же сервер не защищает от потери виртуальной машины. Скачать приватную папку через SSH/SFTP привычным клиентом владельца; не менять права всей директории с секретами на общедоступные. В текущей работе внесерверное копирование не настраивалось и не проверялось.

## Восстановление

Сначала проверить копию в отдельном каталоге, не подменяя рабочие файлы. Тест в репозитории проверяет восстановление небольшой тестовой базы, но не является проверкой реальной пользовательской копии.

1. Остановить `truethrills`. Сохранить текущие повреждённые/новые данные отдельно, чтобы не потерять возможность анализа.
2. Вернуть исходный код к сохранённому до обновления SHA в отдельной ветке. Не применять destructive reset к локальным изменениям.
3. Из проверенной папки восстановить `truethrills.db` и `storage` в пути из `server.env`. Старые `-wal`/`-shm` переносить вместе со старой базой в карантин, не оставлять рядом с восстановленной базой.
4. Восстановить `.env` из `server.env` с правами 600. Проверить пользователя службы и права на базу/аудио. Не заменять секрет подписи сессии и Firebase service account произвольными значениями.
5. `npm ci --include=dev`, `npm run build`, затем запустить службу. Проверить `/api/health`, вход автора, список материалов, реальное проигрывание и донат-ссылку.
6. Убедиться, что timer backup снова включён и новая проверенная копия создана.

## Мониторинг

`truethrills-monitor.timer` запускает проверку раз в 5 минут: HTTPS/health, сертификат, свободный диск, свежесть backup. Результат сохраняется в `data/operations/health.json` и systemd journal.

```bash
sudo systemctl start truethrills-monitor.service
sudo journalctl -u truethrills-monitor.service -n 20 --no-pager
```

Порог диска — 1 GiB, сертификата — 14 дней, копии — 36 часов. Это локальная диагностика. Она **не отправляет отдельное SMS/email/push владельцу** и не сработает, если весь VPS выключен. Для внешнего аварийного уведомления ещё требуется выбранный канал доставки и независимый наблюдатель; не считать задачу завершённой по одному зелёному health.

## TURN на существующем VPS

Сервер `/api/ice` поддерживает coturn REST credentials. Сам coturn на VPS этой работой не установлен. В `TURN-SETUP-RU.md` описана конфигурация, которую нужно проверить с реальными адресами и firewall Oracle.

В `.env` при готовом coturn задаются `TURN_URLS` (через запятую) и `TURN_SECRET` (тот же `static-auth-secret`). Пустые значения оставляют прежний STUN. Автор и слушатель получают свежий пароль при соединении, общий секрет не передаётся клиенту.

До проверки `relay` между Windows и Android на разных сетях нельзя считать TURN рабочим. Он помогает прохождению NAT, не снимает лимит 8 слушателей и не решает фоновый WebRTC на Android.

## Сборки и секреты

- Android Actions: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `GOOGLE_SERVICES_JSON_BASE64`. Секрет `ANDROID_KEYSTORE_PASSWORD` передаётся Gradle как `RELEASE_KEYSTORE_PASSWORD`; это разные имена на разных уровнях. Не переименовывать уже настроенные секреты и не менять ключ подписи.
- На VPS Firebase: `FIREBASE_SERVICE_ACCOUNT_FILE` — путь к приватному JSON. Наличие файла не доказывает полномочия или доставку сообщения.
- Windows Actions: Zig 0.13.0 и закреплённый WebView2 SDK с проверкой SHA256. EXE не подписан коммерческим сертификатом; подпись APK и подпись Windows — разные вещи.
- Артефакты Actions хранятся 30 дней. Для долговременного распространения после приёмки подготовить GitHub Release или загрузку со своего домена. До приёмки не заменять публичную рабочую загрузку тестовым APK.
