# Текущее состояние проекта (снимок на 2026-08-23)

Честный технический снимок Blender Helper на конкретный момент времени —
не архитектурная документация (та живёт в `CLAUDE.md`) и не журнал по
фазам (тот — `PROJECT_PLAN.md`). Цель этого файла — дать быстрый ответ на
вопрос "что тут реально есть прямо сейчас, какого размера и что известно
не так", не читая всю историю проекта. Числа устаревают быстро — сверяйся
с `/stats` в самом боте для актуальных на данный момент значений.

Написан по итогам внешнего hardening-ТЗ (`CLAUDE_CODE_MASTER_TZ.md`,
2026-08-22/23) поверх уже завершённых ТЗ v2 (15 фаз) и ТЗ v3 (5 этапов).

## Архитектура

См. `CLAUDE.md` за полным обоснованием разделения на слои. Коротко:

```
app/main.py       — composition root: сборка Application, регистрация хендлеров
bot/               — Telegram-слой (handlers/*, telegram_output.py, rate_limit.py,
                      news_fetcher.py) — только формат сообщений/диалогов
search/            — SearchEngine (BM25 + термины + версии + authority + chunk_kind +
                      hotkey_intent), QAService (бизнес-логика + Conflict Engine)
intents/           — классификация типа вопроса и темы
diagnostics/       — decision-tree диалоги для проблем
education/         — /learn /test /exam /progress /weaknesses /next
knowledge/         — knowledge chunks: official/manual, personal/dima_notes, system/*
profile/           — SQLite user profile + JSON-подписчики рассылки
config/            — пути, токены, ID владельца (.env)
```

`bot.py` в корне — тонкий совместимый entry point для systemd, не трогать
без обновления деплоя (см. `DEPLOYMENT.md`, раздел 13).

## Search-ранжирование поверх BM25

`search/engine.py` — множители сверх лексического BM25-скора:
`AUTHORITY_MODIFIER_WEIGHT`, `VERSION_MODIFIER_WEIGHT`, `TOPIC_MODIFIER_WEIGHT`,
`CHUNK_KIND_MODIFIER_WEIGHT`, `HOTKEY_INTENT_MODIFIER_WEIGHT`. Последний
(вес 1.0, решающий) — прямое распознавание хоткей-намерения вопроса
(`_is_hotkey_intent`), а не тонкая подстройка scores; добавлен по живой
обратной связи, когда обычный ranking не мог гарантированно вытащить
именно hotkeys-чанк на вопрос вида "какой хоткей делает X".

`CHUNK_KIND_MODIFIER_WEIGHT` (0.2) — эмпирически проверен на 540-кейсовом
Quality Suite (не подкручен вслепую, hardening ТЗ BB-004): обнуление этого
веса роняет Quality Score на 0.82 п.п., целиком за счёт retrieval accuracy,
и меняет реально найденный контент в 68 из 540 кейсов. Механизм оставлен
как есть — второй параллельный механизм ранжирования по типу chunk'а не
нужен, этот уже отрабатывает.

**Search-time collapse дублей (BB-003).** 328 групп chunk'ов с байт-в-байт
одинаковым `content_hash` найдено в базе (см.
`scripts/audit_duplicate_content.py` — отчёт, ничего не удаляет). Причина
в основном ожидаема: одна и та же формулировка параметра дословно
повторяется на нескольких страницах официального Manual. `SearchEngine.
search()` теперь схлопывает такие дубли на этапе выдачи результатов —
пользователь никогда не увидит один и тот же текст дважды в одном ответе,
даже если сами chunks остаются в data-файлах нетронутыми.

## Надёжность (hardening ТЗ, разделы B-G)

- **Безопасный вывод в Telegram** (`bot/telegram_output.py`): HTML
  `parse_mode` вместо Markdown V1, весь динамический текст экранируется,
  безопасное разбиение длинных сообщений по границам тегов/сущностей.
- **Атомарная запись** `profile/subscribers.py` (temp-файл + fsync +
  `os.replace`), повреждённый файл не роняет `/start`.
- **`/quick_add`**: стабильная генерация id (максимум занятого номера + 1,
  не длина списка) и защита от дублей по нормализованному вопросу.
- **`bot/news_fetcher.py`**: `asyncio.Lock` с двойной проверкой против
  cache stampede, per-feed изоляция ошибок, реальный socket-таймаут через
  `urllib.request.urlopen(timeout=...)` (не только `asyncio.wait_for` —
  тот не прерывает уже запущенный блокирующий поток, проверено
  эмпирически), fallback на устаревший кэш при сбое сети.
- **Контекстное распознавание версии Blender** (`extract_version_hint`):
  число засчитывается версией только рядом со словом "Blender"/"версия",
  не любое "число.число" в тексте (было: "2.5 метра" ложно триггерило).
- **Rate limiting** (`bot/rate_limit.py`): простой in-memory лимитер,
  10 запросов/10 секунд на пользователя, OWNER_ID и inline-режим
  освобождены.
- **Education**: кнопки квиза привязаны к конкретному `question_id`,
  устаревшая/повторная кнопка не сбивает счёт и не пропускает вопрос.
- Diagnostics-граф уже полностью валидируется при загрузке (dangling
  references, тупики, несовпадение id) — отдельный аудит подтвердил, что
  чинить нечего.
- Все 10/10 admin-команд и `/broadcast` подтверждены на `OWNER_ID`-проверку.

## Известные ограничения (честно, без приукрашивания)

- **Level System** (раздел 20 ТЗ) не реализован: 3 урока покрывают 1 из
  10 требуемых областей компетенций — присваивать уровень на таком узком
  срезе было бы недостоверно.
- **`ResponseTimeTests.test_answer_latency_within_limit`** — известный
  флейк, случайные запросы из выборки иногда превышают 50мс-порог на
  корпусе 10470+ chunks (обычно 100-270мс на самом медленном запросе в
  выборке). Не блокирует деплой, не паникуем на каждый запуск тестов.
- **`.. reference::`-фикс не распространяется на секцию "Usage"** —
  пошаговые процедурные инструкции под именованными подзаголовками
  ("Usage", "Steps") на страницах Manual по-прежнему не извлекаются ни в
  один вид chunk'а (только intro/reference/note/warning/options). Найдено
  при разборе того же живого бага (Loop Cut), не почищено в этом проходе —
  более рискованное изменение (нужно отличать содержательную процедуру от
  шума типа "Examples"/"See Also"), оставлено на будущее.
- **Таблицы Manual** (`.. list-table::`) сознательно не извлекаются —
  на практике оказались в основном скриншот-галереями, не текстовыми
  данными (см. `scripts/parse_manual.py`, докстринг).
- **328 групп дублей по content_hash** в базе остаются как есть на диске
  (только схлопнуты на этапе поиска) — раздел 21 hardening ТЗ прямо
  запрещает массовые изменения knowledge JSON без воспроизводимого
  ingestion pipeline; решение, что чистить, требует ручного разбора
  отчёта `duplicate_content_report.md`.
- **Сервер слабый** (Oracle Cloud VM.Standard.E2.1.Micro, 952 МБ RAM, без
  swap) — полный `discover tests` на нём падает по OOM (несколько
  тестовых классов держат по своему `SearchEngine` одновременно). Сам
  живой бот строит только один экземпляр (~150-200 МБ RSS) — под
  продакшн-нагрузку безопасно, тесты гоняются локально на дев-машине.
