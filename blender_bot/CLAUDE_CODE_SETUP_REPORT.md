## Обновление 3 (та же дата) — fast_check ПОЧИНЕН, причина: кодировка stdin/stderr

Итог: **все три hook'а, MCP, subagents и skills подтверждены рабочими
через реальный harness.** Ниже — что оказалось настоящей причиной молчания
`fast_check`, найденной инструментированием, а не догадкой.

### Как нашли (метод, а не везение)

Пользователь выполнил `/hooks` и показал вывод: hook **зарегистрирован**
корректно (`Event: PostToolUse`, `Matcher: Edit|Write`, `Source: Project
settings (.claude/settings.json)`, правильная команда). Это сразу
исключило гипотезы про обнаружение конфига и про `if`-поле — искать
надо было внутри самого скрипта.

Ключевое наблюдение, сделавшее диагностику возможной: `settings.json`
не перечитывается посреди сессии, **но сам hook-скрипт запускается
заново на каждый вызов** — значит правки в `fast_check.py` действуют
немедленно, без перезапуска. Поэтому в скрипт была временно добавлена
запись сырого stdin в файл `_hook_diag.log`. Первый же Edit показал, что
hook **вызывается всегда** (`stdin_len=10981`), и в payload'е видно:

```
"cwd":"D:\\РњРѕРё РґРѕРєСѓРјРµРЅС‚С‹\\TG BOT"
```

Это `Мои документы` в UTF-8, прочитанные как cp1251.

### Настоящая причина (две зеркальные ошибки кодировки)

1. **stdin.** Claude Code присылает payload в UTF-8, а Python на Windows
   декодирует текстовый `sys.stdin` в системной кодировке (cp1251).
   `file_path` приезжал как `D:\РњРѕРё РґРѕРєСѓРјРµРЅС‚С‹\TG BOT\...` —
   такого файла на диске нет, проверка `if not path.exists(): return 0`
   срабатывала, и hook **молча выходил с успехом**. Снаружи это выглядело
   ровно как "hook не запускается вообще". Проблема существует только
   потому, что путь проекта содержит кириллицу.
   `guard_destructive` (PreToolUse) той же ошибки не показывал, так как
   сверяет только ASCII-текст команды и не резолвит пути на диске — вот
   почему один hook работал, а другой нет.
2. **stderr.** После починки stdin hook сработал, но весь русский текст
   в сообщении доехал как `??????????`: обратная сторона той же медали —
   Claude Code читает stderr как UTF-8, а Python кодирует текстовый
   `sys.stderr` в cp1251.

### Что исправлено

- `.claude/hooks/fast_check.py`: чтение `sys.stdin.buffer.read().decode("utf-8-sig")`
  вместо `sys.stdin.read()` (`utf-8-sig` заодно съедает BOM, прежний
  хак `.lstrip("\ufeff")` больше не нужен); новая функция `_report()`
  пишет в `sys.stderr.buffer` байтами в UTF-8 — все три места вывода
  (`SyntaxError`, падение теста, внутренняя ошибка хука) переведены на
  неё.
- `.claude/hooks/guard_destructive.py`: то же исправление чтения stdin.
  Здесь баг не проявлялся, но был реальной дырой в защите: деструктивная
  команда, нацеленная на кириллический путь, приезжала битой и могла НЕ
  совпасть с `_PROTECTED_TARGET_RE`, то есть тихо пройти мимо guard'а.
- `.gitignore`: добавлен `.claude/hooks/__pycache__/`.
- Временный `_hook_diag.log` и все тестовые `.py`-файлы удалены.

### Бонусом: ложное срабатывание guard'а, найденное на себе же

При попытке закоммитить всё вышеописанное guard **заблокировал
собственный коммит**: в ТЕКСТЕ commit-сообщения (оно описывает как раз
починку хуков) встречаются слова `rm -rf` и `knowledge/`, а регекс
проверял всю строку команды целиком, не отличая исполняемую часть от
текста сообщения в heredoc'е.

Исправлено узко и осознанно: `_strip_message_bodies()` вырезает тело
heredoc'а перед проверкой, но **только если команда — `git commit`**.
Вслепую вырезать heredoc у любой команды было бы дырой: `bash <<EOF ...
EOF` реально исполняет своё содержимое. Всё вне тела heredoc'а
проверяется как раньше, поэтому `git commit -m "..." && rm -rf
knowledge/` по-прежнему ловится.

Проверено отдельным self-test'ом на 4 кейсах (сам тест пришлось
вынести в файл — Bash-команда с этими словами блокировалась guard'ом,
что само по себе подтверждало наличие проблемы):

| Кейс | Ожидание | Факт |
|---|---|---|
| `git commit`, слова только в тексте сообщения | пропустить | ✅ пропущен |
| `git commit` + реальная деструктивная команда после heredoc | заблокировать | ✅ заблокирован |
| обычное удаление по `knowledge/`, без `git commit` | заблокировать | ✅ заблокирован |
| `bash <<EOF` с удалением внутри (обход) | заблокировать | ✅ заблокирован |

ещё НЕ проверено" из Обновления 2 закрыт полностью.

  "Edit(**/*.py)"`/`"Write(**/*.py)"`, а у сработавшего PreToolUse — `if`

  (правка файла не подхватилась без нового перезапуска) — то есть этот
  конкретный тест ничего не доказал ни в одну, ни в другую сторону.

  неустановленной в рамках этой сессии (для точного диагноза нужен
  `claude --debug`, который требует отдельного перезапуска с этим флагом
  вручную пользователем — не то, что можно включить изнутри сессии).

**Решение, не дожидаясь точного диагноза причины:** оба `if`-условия
убраны из `.claude/settings.json`. Теперь `PostToolUse` для
`matcher: "Edit|Write"` запускает `fast_check.py` БЕЗ фильтра на уровне
Claude Code — фильтрация "это точно `.py`?" и так уже была первой
проверкой внутри самого скрипта (`if not file_path.endswith(".py"):
return 0`), так что поведение для `.py`-файлов не меняется, а
зависимость от непроверенного `if`-механизма исчезает. Это опирается
только на `matcher`-режим, который уже доказанно работает через реальный
harness (см. PreToolUse выше). Одну лишнюю запись объединил в одну (было
два одинаковых хука под `if: Edit(...)` и `if: Write(...)`, стало один
под общий `matcher: "Edit|Write"`).

**Этот фикс ещё раз не проверен в реальном harness** (та же причина:
`settings.json` не перечитывается посреди сессии — попытка проверить сразу
после правки дала тот же немой результат, ожидаемо). Нужен ещё один
перезапуск, затем повторить ровно тот же smoke test: написать `.py`-файл с
синтаксической ошибкой и убедиться, что `fast_check` реально блокирует
(exit 2, текст про `SyntaxError` виден в ответе Claude).

## Обновление (та же дата, новая сессия) — конфиг не подключался, причина найдена и исправлена

Пользователь вернулся в новой сессии с вопросом "это уже работает?" и
попросил полный повторный аудит. Аудит показал: **ничего из раздела
Added ниже пересоздавать было не нужно** — всё это уже существовало и
было правильно написано, но было неактивно по структурной причине, не
из-за содержимого файлов.

### Причина (подтверждена через официальную документацию, не предположение)

Эта сессия запущена из корня git-репозитория (`TG BOT/`), а не из
`blender_bot/` — пользователь подтвердил, что **всегда открывает
родительскую папку**. Весь `.claude/`-конфиг и `.mcp.json` при этом лежали
в `blender_bot/.claude/` и `blender_bot/.mcp.json`. По официальным докам
(`code.claude.com/docs/en/mcp`, `.../hooks`, `.../sub-agents`,
`.../settings`) эти три механизма (в отличие от skills) читаются из
РАЗНЫХ мест:

| Механизм | Где ищется | Результат при cwd=корень, конфиг в blender_bot/ |
|---|---|---|
| Skills | рекурсивно по всему репозиторию (подтверждено: подхватились с префиксом `blender_bot/.claude/skills` в этой же сессии) | ✅ работает |
| Subagents (`.claude/agents`) | walk-up от cwd к корню репо — путь `blender_bot/.claude/agents` при cwd=корень никогда не проходится (walk идёт вверх, не вниз) | ❌ не подключены |
| `.mcp.json` | буквально "the folder you start in" (project root) | ❌ не подключён |
| `.claude/settings.json` (hooks, permissions) | дословно из докки: "Claude Code reads it only from the folder you start in" | ❌ не подключены |

Это объясняет всё: `code-reviewer`/`test-engineer`/`search-quality-reviewer`
не появлялись в списке доступных агентов, Playwright не давал ни одного
`mcp__playwright__*` инструмента, а hooks не срабатывали ни разу — не
потому что что-то было сломано в содержимом, а потому что Claude Code их
физически не читал с этого cwd.

### Второй, независимый баг — найден по ходу, не связан с cwd

`.claude/settings.json` использовал `"if": "Edit(*.py)"` /
`"Write(*.py)"` для fast_check hook. По докам permissions/hooks
(`code.claude.com/docs/en/permissions`, таблица про `*.env`/`*.py`):
одно-сегментный wildcard-паттерн без `**/` матчит ТОЛЬКО файлы прямо в
корне, без пути — `Edit(*.py)` матчит `file.py`, но НЕ
`knowledge/terminology.py`. Почти весь реальный код проекта лежит в
подпапках (`bot/`, `search/`, `knowledge/`, `tests/`...) — то есть даже
если бы cwd-проблема не существовала, fast_check hook почти никогда бы не
срабатывал на реальных правках. Исправлено на `Edit(**/*.py)` /
`Write(**/*.py)` — теперь матчит на любой глубине.

## Added

### 1. MCP — Playwright (`.mcp.json`, project scope)

```json
{
  "mcpServers": {
    "playwright": { "type": "stdio", "command": "npx", "args": ["-y", "@playwright/mcp@latest"] }
  }
}
```

Официальный пакет Microsoft (`@playwright/mcp`), способ подключения
подтверждён через `code.claude.com/docs/en/mcp-quickstart` (не
сторонний/сомнительный MCP). `.mcp.json` — project scope, как просил
пользователь, коммитится в репозиторий (сама документация это прямо
рекомендует для командной работы).

### 2. Hooks (`.claude/settings.json` + `.claude/hooks/*.py`)

Двухуровневая схема, как просил пользователь:

- **Level A** — `PostToolUse` на `Edit(*.py)`/`Write(*.py)`:
  `.claude/hooks/fast_check.py` — compile-check изменённого файла +
  best-effort прогон одного подходящего по имени тестового файла, если
  такой находится. Быстро (секунды), не трогает тяжёлый quality-suite.
- **Level B** — сознательно НЕ реализован как hook. `Stop` срабатывает
  на КАЖДУЮ реплику Claude (не только "конец кодовой задачи") — вешать
  туда `discover tests` (~5 минут) заставило бы ждать 5 минут даже
  простой вопрос без единой правки кода. Вместо этого Level B — skill
  `validate-release` (см. ниже), вызываемая явно перед тем, как считать
  существенную работу готовой к деплою. Это прямое следствие изучения
  документации, не самовольное отступление от запроса — задокументировано
  здесь явно, чтобы решение было видно, а не спрятано.
- Лёгкое ненавязчивое **напоминание** (`Stop` hook,
  `stop_reminder.py`) — не блокирует, не запускает тесты сам, просто
  печатает одну строку, если есть незакоммиченные `.py`-правки. Если
  будет раздражать — можно просто убрать запись `Stop` из
  `settings.json`, больше ничего не сломается.
- **PreToolUse guard** (`guard_destructive.py`) — см. раздел
  Permissions ниже, работает вместе с `permissions.deny`/`ask`, не
  вместо них.

**Реальный баг, найденный на smoke test'е (не в теории):** PowerShell
добавляет BOM-символ при пайпинге строки в stdin внешнего процесса.
`json.load(sys.stdin)` в обоих hook-скриптах падал на этом молча (ловился
широким `except Exception: return 0`) — деструктивная команда проходила
БЕЗ единого сообщения об ошибке, как будто хук вообще не сработал.
Нашёл именно потому, что тестировал по-настоящему (третий кейс из трёх
дал пустой вывод вместо ожидаемого deny-JSON), а не поверил, что скрипт
"должен работать" раз синтаксически корректен. Исправлено —
`sys.stdin.read().lstrip("\ufeff")` перед `json.loads()` в обоих файлах,
перепроверено на трёх случаях (безопасная команда / деструктивная на
защищённый путь / force push, который ловит не этот хук, а
`permissions.deny`) — все три ведут себя как задумано.

### 3. Subagents (`.claude/agents/`)

Три, как просил пользователь, не больше:

- **`code-reviewer`** — только review (`tools` не включает Edit/Write),
  специфика проекта: Telegram/async, атомарность файловых операций,
  knowledge/search-корректность, diagnostics/education state,
  edge cases слабого сервера.
- **`test-engineer`** — анализ покрытия, точечный/полный прогон
  (объясняет реальную команду `unittest`, не выдуманный `pytest`),
  проверка "фикс реально закрывает баг, а не просто зелёные тесты".
- **`search-quality-reviewer`** — не принимает ranking-изменения без
  измерения before/after, явно ссылается на реальный прецедент
  (BB-004 в `IMPLEMENTATION_REPORT.md`) как образец нужного уровня
  доказательности.

### 4. Skills (`.claude/skills/*/SKILL.md`)

Четыре, как просил пользователь:

- **`run-regression`** — Level A по требованию: точечные тесты, решение,
  нужен ли полный gate.
- **`search-quality`** — прогон quality-suite, сравнение с последним
  зафиксированным baseline, явный вердикт по регрессии.
- **`audit-knowledge`** — переиспользует уже существующий
  `scripts/audit_duplicate_content.py` (не изобретает заново), плюс
  проверка метаданных/версий/terminology-коллизий. Ничего не удаляет
  сама — только собирает данные для решения человеком.
- **`validate-release`** — полный Level B: compileall → discover tests →
  (quality-suite внутри того же discover) → ручной smoke-вопрос через
  `QAService` → только затем описывает реальный, уже действующий
  deploy-пайплайн (backup → git pull → restart → проверка
  `journalctl`), с явной оговоркой, что сам деплой — действие с
  реальными последствиями и требует внимания/подтверждения, не слепого
  автозапуска.

### 5. Permissions (`.claude/settings.json`)

`deny` (жёсткий блок):
- Чтение/правка `.env` и `*.key` (SSH-ключ) — Claude физически не может
  затянуть их содержимое в контекст через встроенные файловые
  инструменты. Не мешает уже существующему рабочему процессу — SSH весь
  этот проект вызывался через `ssh -i "путь\к\ключу"` в PowerShell-
  команде (путь как аргумент, не чтение содержимого файла), это не
  трогается.
- `git push --force` / `-f` (Bash и PowerShell формы) и
  `git filter-branch` — без утверждённого исключения через ручную
  правку `settings.json`.
- `git add` секретных файлов — на случай, если `Read`/`Edit`-запрет
  обойдён каким-то иным путём, второй слой защиты.

`ask` (обязательное подтверждение, не блок): `git reset --hard`,
`git branch -D`, `Remove-Item -Recurse -Force` — не всегда опасны (иногда
законная уборка scratch-файлов), но достаточно рискованны, чтобы не
делать их автоматическими без подтверждения.

**Ничего из обычных safe git/python/test команд не тронуто** — `git
commit`, `git push` (без `--force`), `git checkout`, `python -m
unittest`, чтение файлов проекта работают как раньше, без изменений.

### 6. Sentry — рекомендация, не установка

`SENTRY_RECOMMENDATION.md` — что даст, что менять, какие данные уходят
(предупреждение про `update.message.text` в локальных переменных
стектрейса по умолчанию), обязательный `before_send`-скраббер, оценка
трудозатрат (~1-2 часа). Сам Sentry НЕ установлен — ждёт отдельного
подтверждения пользователя, как и было явно указано в задаче.

## How to use

- **Каждый Edit/Write по `.py`-файлу** — после перезапуска сессии
  `fast_check.py` сработает автоматически, ничего вызывать не нужно.
- **В середине работы над правкой** — вызови skill `/run-regression`
  (или попроси "прогони run-regression") для точечных тестов + решения,
  нужен ли полный gate.
- **Перед тем как считать существенную правку готовой к деплою** —
  `/validate-release`. Не после каждого файла, только перед реальным
  деплоем на живой сервер.
- **Меняешь ranking/веса/пороги в поиске** — `/search-quality` ДО того,
  как считать изменение принятым; для code review такого дифа проси
  subagent `search-quality-reviewer`, не обычный `code-reviewer`.
- **Что-то выглядит странно в базе знаний** (дубли, странные ответы) —
  `/audit-knowledge`.
- **После нетривиальной правки кода** — попроси subagent
  `code-reviewer` для независимого взгляда, `test-engineer` — чтобы
  проверить покрытие и что баг реально закрыт, не просто "тесты
  зелёные".
- **Playwright** (после рестарта и `/mcp`-проверки) — попроси открыть
  любую публичную страницу, например `docs.blender.org`, для
  подтверждения перед реальным использованием.
- Деструктивные команды (force push, `rm -rf`/`Remove-Item -Recurse
  -Force` на `knowledge/`/production DB/деструктивные SSH-команды на
  деплой-директорию) теперь либо жёстко заблокированы, либо требуют
  твоего явного да — это не изменит обычный рабочий процесс.
