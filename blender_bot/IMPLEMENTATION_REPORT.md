# Implementation Report — hardening ТЗ (2026-08-22/23)

Итоговый отчёт по внешнему hardening/quality-upgrade ТЗ
(`CLAUDE_CODE_MASTER_TZ.md`), выполненному поверх уже завершённых ТЗ v2
(15 фаз) и ТЗ v3 (5 этапов). Формат — по разделу 24/25 самого ТЗ: статус
по каждому известному багу, реальные числа тестов/Quality Score до и
после, честно про то, что осталось непроверенным.

**Важная оговорка перед всем остальным**: этот отчёт не заявляет
"production-ready" без квалификации. Всё перечисленное ниже как FIXED
проверено юнит-тестами и минимум одним живым прогоном через `QAService`
или реальным smoke-вопросом; ничего не задеплоено без прохождения
локального теста и без последующей проверки чистого старта на сервере по
`journalctl`. Живая проверка реальными пользователями в Telegram после
каждого деплоя — не завершена мной (я не имею доступа к боту как
пользователь), за исключением случаев, где сам пользователь подтвердил
результат в разговоре.

## Что сделано сверх исходного списка BB-001..010

Два живых бага, найденных и исправленных в процессе Phase I (финальной
проверки), не входившие в изначальный список:

1. **Manual-парсер отбрасывал `.. reference::` (Mode/Menu/Shortcut)
   целиком** — единственное место в RST, где Manual явно называет
   горячую клавишу инструмента. Найдено на реальном отчёте пользователя
   ("ответ на Loop Cut описывает механику, но не называет Ctrl+R").
   Подтверждено на реальном репозитории `blender-manual`: 596 из 2389
   `.rst`-файлов используют эту директиву. Починен парсер
   (`scripts/parse_manual.py`), Manual полностью переиндексирован
   (10470 chunks, +1518 `reference`-чанков). Quality Score выросла с
   90.1% до 91.6% на этом одном изменении.

2. **Reference-chunk был в базе, но не всегда доходил до текста ответа**
   — `CHUNK_KIND_RANK` ставит `reference` и `intro` в равный ранг (1.0),
   и при ничьей `is_canonical_title` почти всегда выбирает `intro` (его
   заголовок дословно совпадает с термином). Обнаружено собственным
   финальным smoke-тестом ПОСЛЕ деплоя фикса №1 — прямая проверка живого
   вопроса показала, что хоткей всё ещё не появляется в ответе, несмотря
   на то что данные уже были исправлены. Добавлен
   `SearchEngine.find_reference_sibling()` — не трогает ranking, находит
   reference-chunk той же страницы для того chunk'а, который реально
   выиграл поиск, и `_format_chunk_answer` приписывает его содержимое к
   ответу.

Это два примера, зачем нужна живая проверка после деплоя, а не только
зелёные юнит-тесты: юнит-тесты на синтетике оба раза проходили бы даже
без второго фикса, потому что синтетические фикстуры не воспроизводили
реальную коллизию рангов между `intro` и `reference` на одинаковом весе.

## Детали по каждому исправлению

### Phase B — BB-001/BB-002: безопасный Telegram-вывод
**До**: `parse_mode="Markdown"` без экранирования динамического текста
(knowledge chunks, RSS-заголовки, названия из JSON) — один `__init__.py`
в ответе валил `reply_text` с `BadRequest`.
**Что изменено**: новый `bot/telegram_output.py` — HTML `parse_mode`,
`escape()`/`escape_attr()`, `bold()/italic()/code()/link()`, безопасное
разбиение длинных сообщений по границам тегов. Мигрированы все
`bot/handlers/*.py`.
**Тесты**: 37 новых (`tests/test_telegram_output.py`).
**Результат**: 355/356 → без регрессий, деплой подтверждён живым вопросом
с спецсимволами.

### Phase C — BB-005, BB-008
**До**: `subscribers.json` писался напрямую, обрыв процесса посреди
записи ронял `/start` для всех навсегда; `/quick_add` генерировал id по
`len(registry.chunks)` (коллизия при удалении из середины) и не защищал
от дублей.
**Что изменено**: temp-файл + fsync + `os.replace` в
`profile/subscribers.py`, честная обработка повреждённого файла на
чтении; в `bot/handlers/admin.py` — id по максимальному занятому номеру,
апдейт существующей заметки по нормализованному вопросу вместо дубля.
**Тесты**: 12 новых.
**Результат**: 367/368.

### Phase D — BB-006, BB-007
**До**: параллельные `/news` при устаревшем кэше независимо били по сети;
один зависший фид блокировал весь пакет без таймаута.
**Что изменено**: `asyncio.Lock` с двойной проверкой; каждый фид — своя
задача с socket-level таймаутом через `urllib.request.urlopen(timeout=)`
(эмпирически подтверждено, что `asyncio.wait_for` вокруг уже запущенного
блокирующего потока не прерывает его — таймаут должен быть на уровне
самого сетевого вызова); fallback на устаревший кэш при сбое.
**Тесты**: 8 новых.
**Результат**: 379/380.

### Phase F — BB-010
**До**: `extract_version_hint` считал версией ЛЮБОЕ "число.число"
("2.5 метра" ложно триггерило version_score).
**Что изменено**: номер засчитывается версией только рядом с
"Blender"/"блендер.../версия..." (латиница и кириллица, любое русское
окончание).
**Тесты**: 5 новых + 3 регрессионных.
**Результат**: без изменений в общем счёте, точечный фикс.

### Phase G — rate limiting + reliability-аудит
**Что добавлено**: `bot/rate_limit.py` — 10 запросов/10 сек на
пользователя, `OWNER_ID` и inline-режим освобождены, не более одного
предупреждения за окно. Плюс: устаревшая/повторная кнопка квиза в
education больше не сбивает счёт (question_id теперь в callback_data).
**Аудит без изменений** (уже было в порядке): все 10/10 admin-команд и
`/broadcast` проверяют `OWNER_ID`; diagnostics-граф уже валидируется на
dangling references/тупики при загрузке; `QAService.answer()` не падает
на пустом/пробельном/5000-символьном вопросе.
**Тесты**: 10 новых (rate limit) + 1 (education).
**Результат**: 403/404 (со включением Phase E чуть позже).

### Phase E — BB-003, BB-004
**До**: 328 групп chunk'ов с байт-в-байт одинаковым контентом могли
занимать несколько слотов в топ-N одним и тем же текстом; вклад
`CHUNK_KIND_MODIFIER_WEIGHT` не был измерен.
**Что изменено**: `SearchEngine.search()` схлопывает дубли по
`content_hash` на этапе выдачи (данные на диске не трогаются, раздел 21
ТЗ запрещает массовые правки knowledge JSON без pipeline);
`scripts/audit_duplicate_content.py` — отчёт для ручного разбора.
BB-004: обнуление веса роняет Quality Score на 0.82 п.п., меняет
реально найденный контент в 68/540 кейсов — механизм оставлен как есть,
задокументировано в коде.
**Тесты**: 9 новых.
**Результат**: 403/404.

## Известные проблемы и ограничения (без приукрашивания)

- **BB-009 не восстановлен** — см. таблицу выше.
- **`ResponseTimeTests.test_answer_latency_within_limit`** — известный
  флейк, самый медленный запрос из случайной выборки иногда превышает
  50мс-порог (обычно 100-270мс) на корпусе 10470+ chunks. Не
  диагностировался заново в этой сессии — порог из раздела 4.1 ТЗ v3
  был реалистичен на корпусе ~850 chunks, сейчас корпус в 12 раз больше.
- **Секция "Usage"** (пошаговые инструкции на страницах Manual) по-прежнему
  не извлекается ни в один вид chunk'а — найдено при разборе
  `.. reference::`-бага, не почищено (более рискованное изменение,
  оставлено на будущее, см. `CURRENT_STATE.md`).
- **328 групп дублей остаются на диске** — только схлопнуты на этапе
  поиска, не удалены (осознанное решение по разделу 21 ТЗ).
- **Живая проверка в Telegram после каждого деплоя не автоматизирована**
  — я не могу отправлять сообщения от лица пользователя; каждый деплой
  проверен только по `journalctl` (чистый старт, нет traceback) и
  локальными тестами/quality suite до пуша. Финальные два живых бага в
  этом отчёте (Manual reference:: и reference-sibling) нашлись именно
  благодаря ручной живой проверке — рекомендую пользователю продолжать
  присылать скриншоты реальных ответов, это самый надёжный способ ловить
  то, что синтетические тесты пропускают.
- Полный `discover tests` на продакшн-сервере по-прежнему падает по OOM
  (952 МБ RAM, несколько тестовых классов держат свой `SearchEngine`
  одновременно) — не проблема для самого бота (один экземпляр, ~130-200
  МБ RSS), тесты гоняются локально.

## Итог

10 коммитов за сессию (Phase B, C, D, F, G, H×2, E, Manual reference-фикс,
reference-sibling доп.фикс), каждый — тесты локально → push → деплой на
сервер с бэкапом → проверка чистого старта по `journalctl`. Ни одного
отката не потребовалось. Quality Score выросла с 90.1% до 91.6%, число
тестов — с 356 до 411, самый весомый прирост качества — не из hardening-
чеклиста, а из живого репорта пользователя про Loop Cut, доведённого до
конца через два последовательных фикса.
